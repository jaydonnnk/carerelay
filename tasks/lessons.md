- 2026-09-25: `git merge` chained with `git checkout` in one Bash call was interrupted by the sandbox (SIGTERM from the blocked reg.exe/sc.exe blacklist), leaving the object store truncated and every subsequent `git` command failing with "not a repository". - 2026-09-28: Switching branches (`git checkout main`) deleted **eight tracked files** from the working tree: `docs/ADDITIONAL_CHALLENGE_INFO.md`, `docs/CHALLENGE_REQUIREMENTS_JUDGING.md`, `docs/organiser-tech-load-bearing-audit.html`, `02-adversarial-review.md`, `research-workarounds.md`, and `mockups/{index,03,05}.html`. - 2026-09-30: **A Python rewrite silently converted `tasks/lessons.md` from CRLF to LF, in the same edit that fixed the em dashes above.** The write used `open(p, encoding='utf-8')` to read (universal newlines, so every `\r\n` became `\n` in the string) and `open(p, 'w', encoding='utf-8', newline='')` to write (no translation), so the file was emitted as pure LF. Root cause: `newline=''` was chosen to "preserve" endings, but the endings had already been stripped on read. It was caught only because the worktree was compared against a pre-session backup at `%TEMP%/carerelay-gate4-backup-20260930/tasks/lessons.md`, which showed 9 CRLF and 0 lone LF; the same file is CRLF-clean again after `b.replace(b'\n', b'\r\n')`. **This is the third LF-in-CRLF incident in this project** (see 2026-09-26). **Prevention:** never round-trip a CRLF file through Python text mode. Either read and write in binary (`open(p,'rb')` / `open(p,'wb')`), or read with `newline=''` as well as writing with `newline=''`. After ANY scripted file write, run the byte check on the touched file: `b.count(b'\n') - b.count(b'\r\n')` must be 0 for a CRLF file. Do not trust `git diff` for this, because `core.autocrlf=true` normalises endings on both sides and hides the change entirely. Note the four tracked files that legitimately use LF, so they are not "fixed" by mistake: `.gitignore`, `CareRelay.md`, `ai-triage_casestudy2.md`, `tools/git-switch-safe.sh`. The other 48 tracked files, including this one, are CRLF.

- 2026-09-30: **`git update-ref` silently fails for `refs/remotes/origin/*` under the sandbox, and the ref then vanishes.** After a successful push, `refs/remotes/origin/main` disappeared: `.git/refs/remotes/` was empty, there was no `.git/packed-refs`, `git branch -vv` showed `[origin/main: gone]`, and `git status` comparisons failed with "ambiguous argument 'origin/main...main'". `git fetch origin` reported `* [new branch] main -> origin/main` and the ref then vanished again. **Diagnosis:** `refs/test/x` and `refs/remotes/main` both persisted, but `refs/remotes/origin/main` did not, so the block is on creating a *subdirectory* under `refs/remotes/`. `git update-ref` returns success but writes nothing, which means the sandbox is dropping its lock-file-and-rename sequence. **Workaround that works:** create the directory and write the ref file directly, then verify:
  `mkdir -p .git/refs/remotes/origin` then `printf '<sha>\n' > .git/refs/remotes/origin/main`, and `printf 'ref: refs/remotes/origin/main\n' > .git/refs/remotes/origin/HEAD` for the symbolic ref. Confirm with `git rev-parse refs/remotes/origin/main` and `git rev-list --left-right --count origin/main...main` (must read `0 0`). **Do not conclude the push failed from a missing tracking ref.** The authoritative check is `git ls-remote --heads origin`, which queries the network and does not depend on any local ref. Note also that `git update-ref -d` deletes fine, so cleanup of test refs is unaffected. **The refs do not survive a push, so re-apply this after every one rather than treating it as a one-off:** the manually written refs were present and verified immediately before a second push on 30 September 2026 and were gone immediately after it, so the push itself clears them. Expect `[origin/main: gone]` again after each push and do not read it as a failed push.
- 2026-09-30: **SQLite's `REPLACE` conflict resolution does not fire `BEFORE DELETE` triggers unless the connection sets `recursive_triggers`, and that pragma is per-connection, not stored in the file.** Found by the Slice 3 adversarial review (F1) and fixed the same day (O1). `INSERT OR REPLACE INTO dispositions ...` rewrote `clinical_deadline_utc` from 2026-10-01 to 1999-01-01 with both append-only triggers in place: `PRAGMA recursive_triggers` defaults to `0`, so the implicit delete a `REPLACE` performs is not a trigger-firing delete. `UPDATE` and `DELETE` were refused throughout, so a suite covering only those two verbs stays green while the property does not hold. **Prevention:** when the claim is "this database has no update path", test every statement that can rewrite a row, `INSERT OR REPLACE` included, and prove the refusal with a control that turns the guard off. Never write an unconditional claim about a per-connection pragma: a connection opened outside the module still rewrites the row, so the honest claim names its scope. **Rejected alternative, measured, not assumed:** a `BEFORE INSERT` trigger refusing a colliding insert would close it for any connection, but it also refuses `INSERT OR IGNORE`, because a trigger cannot see the statement's conflict clause and `RAISE(ABORT)` is not overridden by `OR IGNORE`. Probe a stronger-looking guard before adopting it.

Root cause: concurrent read-modify-write on one file, last write wins. It was caught only because the suite came back with 17 red, not by any error from the tool. **Prevention:** issue at most one edit per file per message. After any batch, grep for a marker from each edit before running anything, and treat "successfully edited" as a claim to verify rather than a fact. The same applies to a test run: a green suite after an edit batch proves nothing if an edit never landed.

- 2026-10-04: **A module-level `pytest.mark.skipif` skipped the two tests that needed no database, and they were the two that would have caught the blocker.** `tests/test_postgres_store.py` put `pytestmark = skipif(not _reachable(), ...)` at module scope, so `TestTheTwoSchemasAgree` (which compares two Python string constants and opens no connection) and `TestStatedLimits` were **skipped on every machine without Postgres**, including the one the port was written on. - 2026-10-04: **A DSN whose password is a project name is a placeholder, and the failure looks like a code bug.** The Supabase DSN supplied for the Slice 7b fix pass carried the password `((SH1FTWORK))`, which is the sister project's name in parentheses, not a credential. Every connection attempt failed with `FATAL: password authentication failed for user "postgres"`, and the obvious first hypothesis (percent-encoding, since the password contains parentheses and this exact project had an encoding blocker on 4 October) was **wrong**. **Prevention:** before debugging a credential error as an encoding bug, run the check that separates them: a **keyword-form** connection (`psycopg.connect(host=..., user=..., password=..., dbname=...)`, which bypasses URI parsing entirely). - 2026-10-05: **A mutation record was written from expectation instead of from the run, and it was inverted.** `tests/_mutate_slice7b_stage2.py` recorded all five mutations as RED, and `tasks/todo.md` named S1 and S2 as the RED ones. - 2026-10-05: **A timing assertion with no margin is a flaky test, and it will be reliable on exactly one machine.** `test_the_ddl_is_the_expensive_half_and_d1_removes_it` asserted `connect_only < with_ddl` from one sample of each. On Supabase the DDL costs about 0.97 s, so the inequality never came close to failing; on a local container the whole separation is 10 to 40 ms and connection noise decides it. Measured: one failure in a full-suite run, one failure in 5 isolated runs, roughly 22 per cent. `DEV_DSN` points at a local container, so the flake landed on the project's own documented default engine and not on the one the test was written against. Root cause: the assertion encoded an ordering that was only ever guaranteed by a network round trip, and the guard it was meant to prove (the schema DDL not re-running) has a much larger signature than an ordering. **Prevention:** a timing test must state its margin and take best-of-N on both sides, and the margin must survive on the *slowest* engine anyone runs, not only on the one where it was written. Prefer a ratio or an absolute cost over a strict inequality between two noisy samples. Then run it ten times, not once: a single green run of a timing test is not evidence it is stable.
- 2026-10-05: **A type narrowing done in the annotations only is not a narrowing, and a signature-parity test cannot see it.** Stage 2 recorded that `record_callback_once` had been narrowed from `Origin | str` to `Origin` on Postgres to match SQLite. Measured, Postgres accepted a bare `"local-sim"` and returned `applied` while SQLite raised `AttributeError`. Three helpers still carried `origin.value if isinstance(origin, Origin) else str(origin)`, and three Postgres-only tests passed the bare string, so the suite depended on the permissiveness the record said had been removed. The parity test compared `str(inspect.signature(...))` and stayed green throughout. Root cause: annotations are the only thing a signature test can read, so "the signatures now agree" was treated as "the engines now agree". **Prevention:** a parity claim about types is a claim about the runtime. Prove it by calling both engines with the value that is supposed to be refused, and assert on the refusal and on what was written, not on the annotation. When narrowing, expect it to break: narrowing `_origin_value` alone broke five tests, because `_insert_receipt` and `_append_transition` were handed the *already-validated string* and their `origin: Origin` annotations were simply wrong. Read the call sites before assuming a permissive expression is a widening; it may be an internal contract with a bad annotation.
- 2026-10-05: **A parsed count must never be able to change a verdict, and I reintroduced that exact defect while fixing its record.** While separating SURVIVED from NOT PROVEN in the stage 2 harness, a "how many tests ran" count was added to the verdict as `or ran == 0`. - 2026-10-05: **A documented local port can be permanently unbindable on Windows, and the failure reads like a Docker problem.** `DEV_DSN` in `postgres_store.py` defaults to port 55432, which sits inside a Windows excluded port range (55387 to 55486), so `docker run -p 55432:5432` fails with `ports are not available ...
