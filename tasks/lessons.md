# Lessons

- 2026-09-21: The user is using WorkBuddy for CareRelay. Treat WorkBuddy as the primary organiser product and runtime path; do not default to CodeBuddy. Keep CodeBuddy only as an explicit fallback if the user requests it or WorkBuddy access is proven blocked.
- 2026-09-26: After Git recovery, AGENTS.md still called approved Gate 2 a draft. Root cause: the uncommitted instruction rewrite used the earlier gate snapshot. Prevention: compare gate claims with `00-status.md` and the recovered commit before presenting a commit diff.
- 2026-09-26: A patch introduced LF lines into CRLF AGENTS.md. Root cause: the patch tool preserved surrounding lines but wrote new lines with LF. Prevention: check newline counts after patching CRLF files and normalize only the edited file before diff review.
- 2026-09-26: Two read-only inventory commands failed: PowerShell Get-Item does not support -File, and rg did not expand a Windows path wildcard. Root cause: assuming shell glob and cmdlet behaviour from another command. Prevention: use Get-ChildItem -File for file inventory and rg on the directory with -g for filename filters.
- 2026-09-25: `git merge` chained with `git checkout` in one Bash call was interrupted by the sandbox (SIGTERM from the blocked reg.exe/sc.exe blacklist), leaving the object store truncated and every subsequent `git` command failing with "not a repository". Root cause: the sandbox intercepts binaries mid-pipeline and kills the whole chain, and git had begun rewriting objects. Prevention: run state-changing git operations one per command, never chained with `&&`; verify with `git status` before and after. Never run `git init` or delete `.git` to "fix" a suspected corrupt repo — escalate first.
- 2026-09-28: Switching branches (`git checkout main`) deleted **eight tracked files** from the working tree: `docs/ADDITIONAL_CHALLENGE_INFO.md`, `docs/CHALLENGE_REQUIREMENTS_JUDGING.md`, `docs/organiser-tech-load-bearing-audit.html`, `02-adversarial-review.md`, `research-workarounds.md`, and `mockups/{index,03,05}.html`. Root cause: those files existed on disk and were tracked in `main`'s target commit (`2d7ec71`) but **were absent from `gate-2-architecture`**, so checkout removed them to match the branch. They were **not in any commit reachable from the working branch**, so a naive discard would have destroyed them. **Recovery:** `git checkout HEAD -- <paths>` restored all eight, because HEAD still carried them. **Prevention:** before switching or merging branches, run `git status --short` after the checkout and read it — a non-empty list where a clean tree was expected is a stop signal, not noise. Confirm the destination commit actually contains every file the working tree holds, especially files that predate the current branch. Never run `git checkout .` or `git restore .` to "clean up" before understanding what a deletion means.
- 2026-09-30: **Third git incident, and the worst: the object store was destroyed.** `git` reported "not a git repository" while `.git/` existed. `.git/refs/` was **missing entirely** and `.git/objects/` held **1 loose object plus a commit-graph, with no pack directory** — so no commit was readable. The reflogs in `.git/logs/` survived and proved 11 commits had existed. Root cause: not proven, but the same sandbox interaction as 2026-09-25 is the leading hypothesis — every incident in this project has involved a git state-changing operation under the binary blacklist. **Recovery succeeded** from a Sep 26 backup at `%TEMP%/carerelay-recovery-20260926-190155/ai-triage/.git` (132 objects, all refs intact), which restored 7 commits verbatim; the 2 post-backup commits were re-created from disk. Result: `main` at `96acaa7`, 9 commits, clean tree, 11 tests passing. **Procedure — reuse this, in this order:** (1) `mv .git <temp>` to preserve, never delete; (2) **verify the backup before trusting it** — `git --git-dir=<backup> log --oneline`, `rev-list --count`, `cat-file -e <commit>:<path>` on a known file, never a directory listing alone; (3) `cp -r <backup>/.git .git`; (4) read `git status --short --untracked-files=no` immediately — only `M` is safe, any ` D` means stop; (5) **move the branch ref before switching**: `git branch -f main <target>` while still on the old branch, then `git checkout main`, so both refs sit at one commit and the checkout cannot delete anything (this is the fix for the 2026-09-28 hazard); (6) ignore recovery debris (`.git.SURVIVING-RECORD*/`, `.git.broken*/`, `recovery-*/`) **before** staging — a previous session had left `.git.SURVIVING-RECORD-20260928/` inside the repo and it would have been committed; (7) verify after with `git status`, `rev-list --count` and the test suite. **Standing risk, as of this incident:** there was **no off-machine copy**, and every recovery had depended on a local temp folder left by an earlier incident. **Corrected 30 September 2026:** the risk is closed. `origin` holds `main` and `slice-3` with the gate work, and the pushes of 30 September 2026 succeeded first time. This sentence previously read that `origin` held only `care-relay-adversarial-review` at `2d7ec71` with no gate work, and that pushes had failed on missing credentials; both claims were already out of date when written.
- 2026-09-28: Merge audit of `gate-2-architecture` → `main`. **Verified clean, no repair needed.** `42b5a84` is a true fast-forward with a single parent (`e77d978`), so no merge commit was created and `6c65f30` (Gate 2) is an ancestor of `main`. `gate-2-architecture` was then deleted; its four gate commits (`1cb05c8`, `c01a442`, `6c65f30`, `77ea5ed`) plus `e77d978`, `7c659b0`, `42b5a84` are all reachable from `main` (`a43a091`) and all objects verify present via `git cat-file -e`. Working tree clean, zero untracked files, no stash. Root cause of the near-miss confirmed: the eight files were **never untracked — they were tracked in `2d7ec71`, `9a1f332` and `6c65f30`**, i.e. always in `main` (and in the approved `gate-2-architecture` tip). `git checkout main` did not delete untracked content; it deleted files that branched off `main` **before** `9a1f332`, then titled the Gate 2 and Gate 3 documents using the `02-`/`03-` filenames a second time. **Correction to the earlier log entry:** the lineage was branch-off-`main`, not untracked files surviving via `main`. **Residual exposure:** (a) the working branches still fork before `9a1f332`, so the first `checkout main` from any of them will delete `docs/CHALLENGE_REQUIREMENTS_JUDGING.md`, `docs/ADDITIONAL_CHALLENGE_INFO.md` and `docs/plans/.../02-adversarial-review.md` — run `git branch <name> main` plus `git merge --ff-only main` **before** switching, or `git checkout -m main`; (b) revision-less doc filenames (`02-`, `03-`) collide by design with the `00-`-prefixed gate sequence and caused two different files to share a number — rename durable docs to slugs, not gate numbers. Prevention: before any merge, run `git merge-base --is-ancestor <tip> <target>` and `git log -1 --format=%p <tip>` — two parents means a real merge commit happened and `--ff-only` alone will not catch that after the fact.
- 2026-09-30: **Em dashes were written into new documentation, twice in the same session, against an explicit rule.** `AGENTS.md:264` says "Do not use em dashes in new writing." The Slice 2 completion entries and the Slice 2 review deferral entries used the em dash character in headings and prose (10 added lines across `00-status.md`, `tasks/todo.md` and `slice2-adversarial-review.md`). Root cause: the surrounding documents are full of em dashes (65 in `00-status.md` alone), so mirroring the local style felt correct, and the rule was never checked before writing. The rule is authority; local style is not. **Fix applied:** every added line was rewritten with a colon, comma or parentheses, and verified: `git diff -U0` added lines containing U+2014 = 0, and the review note contains zero U+2014. **Prevention:** before writing any prose into this repo, grep `AGENTS.md` for the writing rules in section 6 and apply them. Do not infer the convention from the existing text. After any doc edit, run the check: `git diff -U0 -- <files> | grep '^+' | grep -c $'\u2014'` must be 0 (use Python for the count; `grep` with the escape does not work in Git Bash). Note that a bare `S` for a slice is banned by the same line, so write `Slice 3`, never `S3`.
- 2026-09-30: **A Python rewrite silently converted `tasks/lessons.md` from CRLF to LF, in the same edit that fixed the em dashes above.** The write used `open(p, encoding='utf-8')` to read (universal newlines, so every `\r\n` became `\n` in the string) and `open(p, 'w', encoding='utf-8', newline='')` to write (no translation), so the file was emitted as pure LF. Root cause: `newline=''` was chosen to "preserve" endings, but the endings had already been stripped on read. It was caught only because the worktree was compared against a pre-session backup at `%TEMP%/carerelay-gate4-backup-20260930/tasks/lessons.md`, which showed 9 CRLF and 0 lone LF; the same file is CRLF-clean again after `b.replace(b'\n', b'\r\n')`. **This is the third LF-in-CRLF incident in this project** (see 2026-09-26). **Prevention:** never round-trip a CRLF file through Python text mode. Either read and write in binary (`open(p,'rb')` / `open(p,'wb')`), or read with `newline=''` as well as writing with `newline=''`. After ANY scripted file write, run the byte check on the touched file: `b.count(b'\n') - b.count(b'\r\n')` must be 0 for a CRLF file. Do not trust `git diff` for this, because `core.autocrlf=true` normalises endings on both sides and hides the change entirely. Note the four tracked files that legitimately use LF, so they are not "fixed" by mistake: `.gitignore`, `CareRelay.md`, `ai-triage_casestudy2.md`, `tools/git-switch-safe.sh`. The other 48 tracked files, including this one, are CRLF.
- 2026-09-30: **The push works. The standing advice that pushes fail on missing credentials is out of date.** `git push origin main` succeeded first time (`6e9be4f..b19b36e`), with a credential helper named `helper-selector` already configured. The "previous pushes failed on missing GitHub write credentials" line had been carried forward since 25 September and was never re-tested. **Prevention:** re-test a stale blocker before repeating it as fact, and label it with the date it was last verified. - 2026-09-30: **`git update-ref` silently fails for `refs/remotes/origin/*` under the sandbox, and the ref then vanishes.** After a successful push, `refs/remotes/origin/main` disappeared: `.git/refs/remotes/` was empty, there was no `.git/packed-refs`, `git branch -vv` showed `[origin/main: gone]`, and `git status` comparisons failed with "ambiguous argument 'origin/main...main'". `git fetch origin` reported `* [new branch] main -> origin/main` and the ref then vanished again. **Diagnosis:** `refs/test/x` and `refs/remotes/main` both persisted, but `refs/remotes/origin/main` did not, so the block is on creating a *subdirectory* under `refs/remotes/`. `git update-ref` returns success but writes nothing, which means the sandbox is dropping its lock-file-and-rename sequence. **Workaround that works:** create the directory and write the ref file directly, then verify:
  `mkdir -p .git/refs/remotes/origin` then `printf '<sha>\n' > .git/refs/remotes/origin/main`, and `printf 'ref: refs/remotes/origin/main\n' > .git/refs/remotes/origin/HEAD` for the symbolic ref. Confirm with `git rev-parse refs/remotes/origin/main` and `git rev-list --left-right --count origin/main...main` (must read `0 0`). **Do not conclude the push failed from a missing tracking ref.** The authoritative check is `git ls-remote --heads origin`, which queries the network and does not depend on any local ref. Note also that `git update-ref -d` deletes fine, so cleanup of test refs is unaffected.
- 2026-09-30: **SQLite's `REPLACE` conflict resolution does not fire `BEFORE DELETE` triggers unless the connection sets `recursive_triggers`, and that pragma is per-connection, not stored in the file.** Found by the Slice 3 adversarial review (F1) and fixed the same day (O1). `INSERT OR REPLACE INTO dispositions ...` rewrote `clinical_deadline_utc` from 2026-10-01 to 1999-01-01 with both append-only triggers in place: `PRAGMA recursive_triggers` defaults to `0`, so the implicit delete a `REPLACE` performs is not a trigger-firing delete. `UPDATE` and `DELETE` were refused throughout, so a suite covering only those two verbs stays green while the property does not hold. **Prevention:** when the claim is "this database has no update path", test every statement that can rewrite a row, `INSERT OR REPLACE` included, and prove the refusal with a control that turns the guard off. Never write an unconditional claim about a per-connection pragma: a connection opened outside the module still rewrites the row, so the honest claim names its scope. **Rejected alternative, measured, not assumed:** a `BEFORE INSERT` trigger refusing a colliding insert would close it for any connection, but it also refuses `INSERT OR IGNORE`, because a trigger cannot see the statement's conflict clause and `RAISE(ABORT)` is not overridden by `OR IGNORE`. Probe a stronger-looking guard before adopting it.
- 2026-09-30: **Four edits were silently lost by issuing several edits to one file in a single message.** The Slice 3 remediation sent two or three edits to `src/carerelay/state.py` per message; every call reported success, and four of them were absent from the file afterwards, including the `PRAGMA recursive_triggers = ON` line the entire fix depended on. Root cause: concurrent read-modify-write on one file, last write wins. It was caught only because the suite came back with 17 red, not by any error from the tool. **Prevention:** issue at most one edit per file per message. After any batch, grep for a marker from each edit before running anything, and treat "successfully edited" as a claim to verify rather than a fact. The same applies to a test run: a green suite after an edit batch proves nothing if an edit never landed.
- 2026-09-30: **The sweep after a push has to cover claims about `origin`'s branch set, not just the word "pushed".** Publishing `slice-3` falsified three sentences that a grep for `uncommitted|not pushed` never found: `AGENTS.md` and `00-status.md` both said `origin` held *exactly one branch*, `refs/heads/main`, and `00-status.md` also said `slice-3` had no upstream of its own. All three were true when written and all three died the moment a second branch was published. **Prevention:** after any push, grep the tracked prose for `origin`, `upstream`, `in sync`, `ahead`, `behind`, `one branch` and `refs/heads`, not only for "pushed". Check the fresh-session notes first, because that is what the next session reads before anything else. The durable fix is to describe the shape of the state ("`origin` holds the branches that hold the work") rather than a count or a hash: a count and a hash both go stale on the next push, and this project has now paid for that twice.
