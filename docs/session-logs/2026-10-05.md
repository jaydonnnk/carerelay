# 2026-10-05

## The blocker in front of the Slice 7b post-ship commit: a poisoned bytecode cache

`tests/test_postgres_store.py::TestTheRecordCannotBeAltered::test_delete_is_refused_on_every_table`
failed with `DID NOT RAISE RestrictViolation` on `episodes`, the first of 14 tables.
Every server-side check said the guard was intact (42 triggers, `tgenabled='O'`,
`session_replication_role=origin`, `carerelay_refuse_write()` holding its RAISE), and a
standalone script on the same DSN raised correctly.

**Root cause, verified.** `tests/__pycache__/_postgres_probes.cpython-313.pyc` held
`DELETE FROM {} WHERE false`; the working file and `git show HEAD` both held
`WHERE true`. Python validates a `.pyc` against the source's **mtime and size only**,
never its content, and mutation P7 of `tests/_mutate_slice7b.py` changed neither:
`WHERE false` is one byte longer than `WHERE true`, and `_anchor` returns the
replacement in LF form against a CRLF file, one byte shorter, so the two cancel; the
write and the restore also landed in the same clock second. The probe matched no row,
so no row-level trigger fired. The guarantee was never broken; the probe never reached it.
Exactly the failure mode the probe's own docstring exists to prevent.

**How it was found.** `pytest -l` (showlocals) showed `table = 'episodes'`, so it failed
on the first iteration. A replica of the fixture outside pytest raised on all 14; the same
fixture inside pytest did not. Then `DELETE FROM episodes WHERE true` as a raw string
raised while `probes.refuse_delete("episodes")` did not, on the same connection in the
same transaction. `inspect.getsource` agreed with the file, so the decisive check was the
loaded code object: `probes.refuse_delete.__code__.co_consts` → `'DELETE FROM {} WHERE
false'`. `inspect.getsource` reads the file and will agree with the file even while the
interpreter runs something else.

**Fixed** by deleting four `__pycache__` directories: 613 passed, 0 skipped. The counts
already written into `00-status.md` and `todo.md` (613 / 0) are true again and were not
changed.

**Hardened** `tests/_mutate_slice7b.py`: `PYTHONDONTWRITEBYTECODE=1` on every child
process, plus `_purge_bytecode(target)` after each restore, which also self-heals a cache
poisoned before the run. Re-run: 6 RED, 1 documented engine constraint, 0 NOT PROVEN of 7,
all three files restored byte-identical. **Residual exposure, recorded in lessons.md:**
`_mutate_slice6.py`, `_mutate_slice7.py`, `_mutate_a7.py` and `_mutate_slice7b_stage2.py`
write and restore by the same pattern and were not changed.

**F10, the narrowed duplicate handler.** `record_expiry_once` wrapped its whole write
block in `except psycopg.errors.UniqueViolation: return False`, so a duplicate raised by
the `events` audit write came back as "already recorded". It now wraps only the
`INSERT INTO expiry_events`, inside `SAVEPOINT expiry_events_insert` plus `ROLLBACK TO`.
**The savepoint is load-bearing:** catching and carrying on without it leaves the
transaction aborted, the `commit` in `_write` then fails, and the caller gets a driver
error where the product promises `False`. Cost is two round trips on any call reaching
the INSERT.

**The test.** `TestTheDuplicateHandlerCoversOnlyItsOwnDuplicate` uses `monkeypatch` to
make `store._append_event` raise a synthetic `UniqueViolation`. Under the old code the
call returned `False`; it now propagates and the expiry row is provably absent (the two
writes are one transaction). It is the only test in the module that reaches
`_append_event` from inside `record_expiry_once`, which is why mutation S6 works.

**Mutation S6 added** (`_mutate_slice7b_stage2.py`, six mutations now): re-broadening the
handler over the audit write. **Final run: 6 RED, 0 SURVIVED, 0 NOT PROVEN**, S6 killed

assert uniqueness.**
