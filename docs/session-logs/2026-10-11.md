## Supabase connection choice for Render (commit e2b1549)

Supabase maps every **Direct connection** string to an IPv6 address, and Render is
IPv4-only: Supabase's own troubleshooting page names Render in the list of
platforms that only accept IPv4. So the Direct connection tab cannot work from the
Render service. Use the **Session pooler** (Supavisor session mode, port 5432 on
the `aws-0-<region>.pooler.supabase.com` host), which is also what the project
verified at Slice 7b stage 1 on both pooler ports. Transaction pooler (6543) is
the wrong shape for this store, which holds a session, applies DDL once, and uses
savepoints and `SELECT ... FOR UPDATE`. Recorded in `submission/setup-runbook.md`.

## CORRECTION: removing `plan: starter` does NOT make the service free

Found on 11 Oct 2026, after commit `ffdffd2`. Render's own blueprint reference
(`render.com/docs/blueprint-spec`, section "If you omit this field") states that
when `plan` is omitted Render uses **`0.5c-512mb`** for a new web service. That is
the **$7/month** tier, not the free one. The valid free plan ID is the literal
string `free` (0.1 CPU, 512 MB, $0/month).

So two documents now carry a false claim and must be corrected:

- `render.yaml` lines 22 to 29: "With no disk the service runs on the free tier".
- `submission/setup-runbook.md` lines 23 to 24: "no longer declares a disk or
  `plan: starter`, so the service runs on the free tier".

The one-line fix is to add `plan: free` to the service block in `render.yaml`.
No test asserts anything about `plan` (grepped `tests/`), and the six tests that
read `render.yaml` are all indifferent to it, so the addition is safe.

Note: "Render retains the current compute plan for an existing service", so an
already-created Free service keeps Free. The $7 lands only on a fresh Blueprint
deploy, which is exactly the path `setup-runbook.md` Part A instructs.

### The Vercel URL trap: `carerelay.vercel.app` is someone else's project

`https://carerelay.vercel.app` **resolves with HTTP 200** but is a different app:
its title is `CareRelay` plus the words `Hospital Staff Portal`. The real frontend
is `https://carerelay-self.vercel.app`. The wrong one was recorded in seven files,
including the submission's own "Live frontend" row, so the submission link pointed
at a stranger's app. Both hosts were fetched to tell them apart; a 200 is not
evidence of ownership. **Always fetch and read the title before trusting a URL.**

### The runbook's auth check could not fail

Step 5 said to `GET /api/episodes` and expect 401 or 503. `/api/episodes` is
POST-only, so a GET answers **405** whether auth is armed or not. The check read
that 405 as a pass. Fixed to check `POST /api/episodes` and
`GET /ledger/demo-episode-001`, both 401 without a token.

### `_OPEN_EPISODES` is process memory, not the store

`api.py:312` holds `_OPEN_EPISODES` as a module-level `set`, and only
`POST /api/episodes` adds to it. After a redeploy or a free-tier spin-down the set
is empty, so `GET /api/episodes/{id}` answers **404** until something POSTs. The
Vercel patient page calls `createEpisode()` before `getEpisode()`, so the demo
recovers by itself. Do not read a 404 there as a persistence failure.

**Not run**, deliberately. The only episode the API can create is the hardcoded

would permanently pre-assess the demo episode and a judge's own intake would then
