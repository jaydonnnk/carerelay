## What B3 actually was

`service.py:318` read `if self._bound_complaint not in rules.normalise(confirmed_text)`
 --  a substring test, so recognition was "does the phrase appear anywhere" rather than
"is this the bound complaint". The Slice 4 review had already measured the damage:
`"help sorting out my appointment, also I have chest pain and cannot breathe"` scored
**200 and issued the demo plan**, as did a stroke text, a negated text and a
third-party text.

**Fix:** `rules.normalise(confirmed_text) != self._bound_complaint`. The system now
refuses strictly more inputs, and a refusal is never a clinical claim, so no reviewer
is needed.

### Harness repair, 3 October 2026 (same day, on the user's "can u do both")

Fixed `tests/_mutate_slice6.py` AND kept V-4 as a carried note.

- **Root cause of the harness failure, established exactly.** `Path.read_text()`
  applies universal-newline translation (CRLF -> LF in memory); `write_text()`
  then wrote **pure LF** back over a CRLF file. So every mutation silently
  converted its target to LF, and the restore was never byte-exact. Separately,
  M11/M12/M13 anchors were written with `\n` and could not match the CRLF file,
  which is why M11 printed `[SKIP]`.
- **The fix:** binary I/O (`read_bytes`/`write_bytes`), a `_b()` helper that
  normalises every anchor to CRLF in one place, a **hard failure** on a missing
  or non-unique anchor (a skipped mutation can no longer pass), an md5-verified
  restore that aborts the run on mismatch, and a control that compares every
  mutated file against its pre-run bytes.
- **Re-run result: 11 of 11 RED** (M11 now runs), control green, all four mutated
  files byte-exact and still CRLF (`state.py` `1dcc54ea...`, `tools.py`,
  `service.py`, `simulated_provider.py`). Suite 484 pass.
- **NOTE: the repaired harness is slow.** M13 alone ran 563 s (was 250 s when it
  was short-circuiting). A full run is ~11 min. Run it in the background.
- **V-2 fully explained now:** the `state != "granted"` branch is pinned by the
  API test; the `version != stamped_version` branch is pinned by
  `test_state.py:1093 test_a_changed_consent_version_also_blocks` (asserts the
  exact string "changed from 1 to 3"). Both are load-bearing, at different layers;

## Slice 7b Stage 1: the Postgres append-only probe, 4 October 2026

**The single most valuable result of the day. Run before writing any store code.**

Environment: `postgres:17-alpine` in Docker on port 55432, user/db `carerelay`,
name `carerelay-pg`. `psycopg 3.3.6` installed into the managed env.

**Raw SQL probe results [verified by running them]:**

| Probe | Result |
|---|---|
| `BEFORE UPDATE` row trigger | Refused: `probe is append-only: UPDATE is refused` |
| `BEFORE DELETE` row trigger | Refused |
| `ON CONFLICT (k) DO UPDATE` | **Refused** via the UPDATE trigger. This is the O1 equivalent, confirmed rather than assumed |
| `ON CONFLICT (k) DO NOTHING` | `INSERT 0 0`, no error, no change. Correct |
| **`TRUNCATE probe`** | **SUCCEEDED. The table was emptied.** |
| `TRUNCATE` with a `BEFORE TRUNCATE ... FOR EACH STATEMENT` trigger | Refused, rows survived |
| `BEFORE TRUNCATE ... FOR EACH ROW` | Postgres errors: "TRUNCATE FOR EACH ROW triggers are not supported" |

**🚨 The finding: moving to Postgres would INTRODUCE a way to erase the append-only
record.** Row-level `BEFORE DELETE` triggers do not fire for `TRUNCATE`, which is a
DDL-level operation. SQLite has no `TRUNCATE` statement, so this vector **did not
exist** in the current system. A naive port would have shipped a weaker guarantee
while looking identical on every existing test.

**The fix is a third trigger per table**, statement-level, generated alongside the
other two:

```sql
CREATE TRIGGER <table>_no_truncate BEFORE TRUNCATE ON <table>
    FOR EACH STATEMENT EXECUTE FUNCTION carerelay_refuse_write();
```

`DROP TABLE` still works, so the schema remains rebuildable.

**Lesson for the skill:** porting a safety property to a new engine is not a
translation. The new engine has a *larger* attack surface, and the strongest claim in
the product was the thing exposed to it. Prove the property on the new engine BEFORE
porting the code that depends on it.

**Second lesson:** the O1 defence (`INSERT OR REPLACE` refused by the DELETE trigger
via `recursive_triggers`) does NOT port as reasoning. The mechanism is different:
Postgres routes `ON CONFLICT DO UPDATE` through the UPDATE trigger. Same outcome,
different cause. It had to be re-proven, and the plan said so before the probe ran.

### 🚨 The defect found while writing the tests, and it is the same class as A7-1

The first UPDATE and DELETE probes used `WHERE false`, reasoning that a refusal is
raised regardless of whether a row matches. **It is not.** A `FOR EACH ROW` trigger
fires per row, and `WHERE false` matches no rows, so **all fourteen tables reported
silence**. The tests passed only because `pytest.raises` was satisfied by the
surrounding loop's rolled-back state. Measured, not theorised: the loop printed
`NO RAISE` for every table.

A second layer was hiding under it: `UPDATE ... SET id = id` named `id`, which
`policy_versions` does not have (its key is `version`), so that table raised
`UndefinedColumn` while the test was asserting only `RestrictViolation`.

**Fix:** `seed_one_row()` writes a real row (and its FK parents) so the trigger has
something to fire against, and the probe column is read from the catalogue rather
than hard-coded. Seeding needed three further corrections, each measured:
`DEFAULT VALUES` fails on all 14 tables (every one has `NOT NULL` with no default);
type-only sentinels violate 14 `CHECK`s (`origin`, `state`, `hint_level` are enums),
so the allowed set now comes from `pg_get_constraintdef`; and `callbacks` has
cross-column `CHECK`s that a per-column picker cannot satisfy, so it is seeded by
hand. All 28 probes (14 UPDATE + 14 DELETE) now genuinely refuse.

**New class `TestTheProbesReachTheGuard`** is the control: it asserts the seed wrote
a row and that `UPDATE ... WHERE true` has `rowcount == 1` while the old `WHERE false`
has `rowcount == 0`. Without it the seeding can regress invisibly.

### The `TRUNCATE` correction, which changed the diagnosis

The 4 original failures were not a cascade-order accident, as first thought.
Measured: `TRUNCATE escalations CASCADE` reaches **only** `escalations`, yet the
`dispositions` FK blocks a bare `TRUNCATE` before any trigger runs
(`FeatureNotSupported: cannot truncate a table referenced in a foreign key
constraint`). And `TRUNCATE episodes CASCADE` reaches **all 14** tables, firing each
one's statement trigger.

So: `refuse_truncate` must use `CASCADE` (a bare `TRUNCATE` raises for the wrong
reason), and the control must drop **every** `_no_truncate` trigger, not just
`episodes`'. Both are now recorded in docstrings at the point of use.

### Latency: the real cost of moving to Supabase

Measured, median of 5 connects and 20 queries:

| Engine | connect | `SELECT 1` |
|---|---|---|
| local docker | **28.5 ms** | **0.48 ms** |
| Supabase pooler (ap-southeast-2) | **2223 ms** | **245 ms** |

**Roughly 78x on connect and 500x on a trivial query.** The 56x suite slowdown is
this, not the tests. Two consequences for the deployment and worth stating before
the switch:

1. **Every request opens a connection today.** `PostgresEpisodeStore.__init__` connects
   and runs the full schema + 42-trigger DDL. At ~2.2 s per connect, that is a
   non-starter for a request path. The store needs a connection that is opened once
   and held, or a pool, before anything goes public.
2. **`lock_timeout = '5s'` is now in the same range as network latency.** 245 ms per
   statement means a handful of statements can approach the lock budget on a slow
   link. The 5 s figure was chosen against a 0.5 ms local engine and should be
   revisited rather than inherited.

These are stage 2 decisions. Recorded here because they are the strongest argument
for keeping the store open across requests, and they were not visible on the local
container.
