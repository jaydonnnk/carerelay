### Procedure that worked (reusable)

1. **Preserve, don't delete.** `mv .git <temp>` — the damaged tree may still hold salvageable objects.
2. **Verify the backup before trusting it.** `git --git-dir=<backup> log --oneline`, `rev-list --count`, and `cat-file -e <commit>:<path>` on a known file. Do not restore on the strength of a directory listing.
3. **Restore by copy:** `cp -r <backup>/.git .git`.
4. **Read `git status --short --untracked-files=no` immediately.** Only `M` entries are safe. Any ` D` means the restore is about to lose files — stop.
5. **Move the branch ref *before* switching.** `git branch -f main <target>` while still on the old branch, then `git checkout main`. Both refs at the same commit makes the checkout a no-op that cannot delete anything. This is the fix for the 28 Sep deletion hazard.
6. **Ignore recovery debris before staging:** `.git.SURVIVING-RECORD*/`, `.git.broken*/`, `recovery-*/`. A previous session had left `.git.SURVIVING-RECORD-20260928/` inside the repo; it would have been committed.
7. **Verify after:** `git status` blank, `rev-list --count`, tests still pass.

### Correction: the deferred-transaction failure mode, measured

The line above says a deferred transaction "would let both read no such key". **That is wrong**, and
the probe that falsified it is worth keeping. `BEGIN IMMEDIATE` appears exactly **once** as
executable code, inside the shared `_write` helper (line 491); the other four occurrences are
docstrings. So the experiment is **one mutation applied to several tests**, not several independent
mutations, and it was reported that way.

Result, with controls, md5-restored after each:

| Mutation | callback race | expiry race | callback single-writer | expiry single-writer |
|---|---|---|---|---|
| none (baseline) | GREEN | GREEN | GREEN | GREEN |
| `BEGIN IMMEDIATE` -> `BEGIN` | **RED** | **RED** | GREEN | GREEN |
| `busy_timeout 5000` -> `0` | **RED** | - | GREEN | - |

**Actual failure mode:** `[OperationalError('database is locked'), True]`. Under a deferred `BEGIN`
the second writer does not silently duplicate; it takes a shared lock, then **crashes on the upgrade
to a write lock** (SQLite does not retry a lock upgrade, because retrying could deadlock). So
`BEGIN IMMEDIATE` is what converts a hard failure into the correct idempotent answer (`False`,
meaning "already received"). The claim is now stronger and more precise than "a deferred
transaction would let both read no such key".

**The control is what makes it mean anything.** The single-writer tests stay GREEN under the same
mutation, so the mutation is specifically a *concurrency* mutation, not one that breaks all writes.
A mutation two checks can both catch proves neither.

Recorded in `00-status.md` as a new evidence row plus a sharpened R6 row, and in the "what this
evidence does not prove" paragraph.

**O1 root cause, verified by probe rather than taken from the review.** `PRAGMA recursive_triggers`
defaults to `0`; SQLite runs the implicit delete a `REPLACE` performs only when it is `1`; and the
pragma is **per-connection, not stored in the file** (a fresh connection to the same file reads
`0`). So `INSERT OR REPLACE` rewrote `dispositions.clinical_deadline_utc` to `1999-01-01` with both
append-only triggers in place. Fix: set the pragma in `SqliteEpisodeStore.__init__`. The claim in
`state.py` and `00-status.md` was then **corrected rather than kept**, because the pragma does not
cover a connection opened outside the module.

**A stronger guard was probed and rejected.** A `BEFORE INSERT` trigger refusing a colliding insert
closes it for any connection, but it also refuses `INSERT OR IGNORE`: a trigger cannot see the
statement's conflict clause, and `RAISE(ABORT)` is not overridden by `OR IGNORE`. Measured. The
false positive would refuse harmless idempotent inserts, including the suite's own seeding helper.
